## 1. SCADA: Konvensional kepada SCADA Berteraskan AI

### 1.1 Apakah Sistem SCADA?

**SCADA (Supervisory Control and Data Acquisition)** adalah sistem pengawasan dan kawalan yang digunakan secara meluas dalam industri untuk memantau dan mengawal proses yang tersebar secara geografi. Komponen utama SCADA:

| Komponen | Fungsi | Contoh |
|---|---|---|
| **MTU (Master Terminal Unit)** | Pusat pengawalan utama | Pelayan SCADA di bilik kawalan |
| **RTU (Remote Terminal Unit)** | Pengumpul data di lokasi jauh | Kotak kawalan di stesen pam |
| **PLC** | Kawalan logik automatik | Siemens S7-300, Allen-Bradley |
| **HMI** | Antara muka visualisasi untuk pengendali | Skrin sentuh di lantai kilang |
| **Rangkaian Komunikasi** | Menghubungkan semua komponen | Modbus TCP, PROFINET, 4G LTE |
| **Pangkalan Data Sejarah** | Menyimpan data proses jangka panjang | OSIsoft PI System, Wonderware Historian |

### 1.2 Batasan SCADA Konvensional

SCADA konvensional direka untuk **pemantauan dan respons reaktif** — pengendali melihat penggera (alarm) dan bertindak balas. Batasan utamanya:

- **Beban penggera (alarm fatigue):** Kilang besar boleh menjana ribuan penggera sehari, menyebabkan pengendali mengabaikan penggera penting
- **Tiada ramalan:** Sistem sedia ada hanya tahu apabila sesuatu **sudah** berlaku, bukan apabila ia **akan** berlaku
- **Analitik terhad:** Data dikumpulkan tetapi tidak dianalisis secara automatik untuk mencari corak
- **Antara muka tidak mesra pengguna:** HMI lama menggunakan grafik statik yang sukar ditafsirkan

### 1.3 SCADA Berteraskan AI (AI-Enhanced SCADA)

**SCADA berteraskan AI** menambahkan lapisan kecerdasan kepada sistem SCADA sedia ada melalui integrasi modul AI. Ini **tidak menggantikan** SCADA — ia menambah nilai di atasnya.

#### Empat Modul AI Utama untuk SCADA:

**Modul 1 — Pengesanan Anomali Adaptif (Adaptive Anomaly Detection)**
- Model ML (Isolation Forest, LSTM Autoencoder) belajar corak operasi normal
- Mengesan sisihan daripada corak normal secara automatik
- Menghantar penggera bermakna sahaja (bukan semua penggera)
- *Kesan:* Mengurangkan alarm fatigue sebanyak 40–60% (berdasarkan kajian implementasi industri)

**Modul 2 — Ramalan Proses (Process Prediction)**
- Model deret masa meramalkan nilai proses masa hadapan (tekanan, suhu)
- Memberi amaran kepada pengendali *sebelum* nilai melebihi had kritikal
- Membolehkan tindakan pencegahan berbanding tindak balas reaktif

**Modul 3 — Pengurusan Penggera Pintar (Intelligent Alarm Management)**
- AI mengklasifikasikan keutamaan penggera mengikut konteks operasi
- Menyaring penggera palsu (false alarms) secara automatik
- Mempamerkan hanya penggera yang perlu tindakan segera kepada pengendali

**Modul 4 — Cadangan Tindakan (Action Recommendation)**
- AI mencadangkan tindakan optimum berdasarkan konteks (beban, suhu, masa)
- Pengendali masih membuat keputusan akhir — AI hanya memberi cadangan
- Penting: dalam sistem kawalan OT, **AI tidak boleh mengambil tindakan kawalan secara autonomi tanpa kelulusan manusia** untuk fungsi kritikal

## 2. Evolusi HMI: Dari Panel Kawalan ke Antara Muka Pintar

### 2.1 Generasi HMI

**HMI (Human-Machine Interface)** adalah antara muka yang membolehkan pengendali kilang berinteraksi dengan sistem kawalan. Evolusinya:

| Generasi | Teknologi | Ciri Utama | Had |
|---|---|---|---|
| **Gen 1 — Analog Panel** | 1960–1980 | Meter, lampu, suis fizikal | Maklumat terhad; perlu latihan intensif |
| **Gen 2 — CRT/Skrin PC** | 1980–2000 | Grafik proses statik, mimik diagram | Tidak responsif; antara muka tidak intuitif |
| **Gen 3 — Skrin Sentuh** | 2000–2015 | SCADA grafik, penggera digital | Data banyak tetapi analitik terhad |
| **Gen 4 — Intelligent HMI** | 2015–kini | AI, AR, papan pemuka kontekstual | Perlu infrastruktur data yang matang |

### 2.2 Ciri-ciri Intelligent HMI

**Intelligent HMI** (atau Smart HMI) menggabungkan kemampuan berikut:

**a) Papan Pemuka Kontekstual (Contextual Dashboard)**
- Paparan automatik berubah mengikut situasi operasi (permulaan, pengeluaran penuh, penyelenggaraan)
- Pengendali tidak perlu navigasi manual ke skrin yang relevan

**b) Analitik Tertanam (Embedded Analytics)**
- Trend masa nyata dengan pengesanan anomali dipaparkan terus pada HMI
- Bukan sekadar nilai semasa — tetapi konteks sejarah dan ramalan

**c) Panduan Augmented Reality (AR Guidance)**
- Tablet atau cermin mata AR menunjukkan arahan penyelenggaraan bertindih di atas mesin sebenar
- Teknologi: PTC Vuforia, Microsoft HoloLens 2, Siemens SiGREEN AR

**d) Natural Language Interface**
- Pengendali boleh menaip atau bertutur "tunjukkan suhu pam P-103 sejak semalam"
- AI mentafsirkan pertanyaan dan memaparkan data yang relevan

### 2.3 Keperluan Infrastruktur untuk Intelligent HMI

Intelligent HMI memerlukan asas data yang kukuh:

1. **Data historian** yang berfungsi dengan baik dan diindeks dengan baik
2. **Integrasi OPC-UA** untuk data pelbagai sumber secara seragam
3. **Model data kilang (semantic model)** — setiap tag data mempunyai nama bermakna, bukan hanya nombor register
4. **Sambungan data lake** untuk analitik sejarah mendalam

## 3. Tadbir Urus Data Kilang Pintar (Smart Factory Data Governance)

### 3.1 Mengapa Tadbir Urus Data Penting?

Kilang pintar menghasilkan **jumlah data yang besar** — sensor suhu, video kamera kualiti, rekod pengeluaran, data ERP. Tanpa tadbir urus yang baik:

- Data daripada sumber yang berbeza tidak boleh digabungkan (format berbeza, nama berbeza)
- Tiada siapa yang tahu data mana yang boleh dipercayai
- Data sensitif (data pekerja, data pelanggan) mungkin diakses oleh pihak yang tidak sepatutnya
- Audit dan pematuhan regulasi (PDPA 2010) menjadi sukar

### 3.2 Lima Dimensi Tadbir Urus Data Kilang

**Dimensi 1 — Pemilikan Data (Data Ownership)**

Setiap set data mesti mempunyai pemilik yang jelas:

| Data | Pemilik | Tanggungjawab |
|---|---|---|
| Data sensor mesin | Jabatan Pengeluaran | Pastikan sensor dikalibrasi dan data tepat |
| Data kualiti produk | Jabatan QA/QC | Pastikan rekod QC lengkap dan tepat |
| Data tenaga | Jabatan Fasiliti | Pastikan meter dikalibrasi |
| Data pekerja | Jabatan HR | Pastikan pematuhan PDPA 2010 |
| Data ERP | Jabatan IT | Integriti dan keselamatan data perniagaan |

**Dimensi 2 — Kualiti Data (Data Quality)**

Empat dimensi kualiti data yang perlu dipantau:

| Dimensi | Definisi | Contoh Masalah |
|---|---|---|
| **Ketepatan (Accuracy)** | Data mencerminkan realiti dengan betul | Sensor rosak menghantar nilai palsu |
| **Kelengkapan (Completeness)** | Tiada nilai yang hilang | Sensor offline selama 2 jam — gap dalam data |
| **Ketepatan Masa (Timeliness)** | Data tersedia apabila diperlukan | Data sensor lewat 5 minit ke dashboard |
| **Konsistensi (Consistency)** | Data yang sama tidak bertentangan antara sistem | Suhu 75°C dalam SCADA tetapi 72°C dalam ERP |

**Dimensi 3 — Kawalan Akses (Access Control)**

Prinsip least privilege — setiap pengguna hanya dapat akses kepada data yang perlu untuk kerjanya:

| Peranan | Akses Data Dibenarkan |
|---|---|
| Pengendali Lantai Kilang | Data masa nyata mesin yang dikendalikan sahaja |
| Jurutera Penyelenggaraan | Data sejarah semua mesin; rekod penyelenggaraan |
| Pengurus Kilang | Semua data operasi; KPI dan laporan |
| Penganalisis Data | Data yang dianonimkan untuk analitik; tiada data HR |
| Pentadbir IT | Semua data (kawalan infrastruktur) |

**Dimensi 4 — Metadata dan Katalog Data (Data Catalogue)**

Setiap dataset perlu didokumentasikan dalam katalog data:

```
Nama Dataset    : sensor_suhu_pam_P103
Sumber          : PLC Siemens S7-300, Tag DB1.DBD0
Kekerapan       : 1 bacaan / 10 saat
Unit            : Darjah Celsius (°C)
Had Normal      : 40°C – 85°C
Had Penggera    : > 90°C (Kritis), > 80°C (Amaran)
Pemilik         : Jabatan Pengeluaran
Tempoh Simpanan : 3 tahun (operasi), 7 tahun (audit)
Sensitiviti     : Tidak sensitif
```

**Dimensi 5 — Pengekalan dan Pembuangan Data (Retention and Disposal)**

| Jenis Data | Tempoh Simpanan Disyorkan | Justifikasi |
|---|---|---|
| Data sensor masa nyata (raw) | 90 hari | Kos storan tinggi; digantikan dengan data agregat |
| Data agregat (jam/hari) | 5 tahun | Analitik trend jangka panjang |
| Rekod penyelenggaraan | 7 tahun | Pematuhan DOSH/OSHA 1994 |
| Data kualiti produk | Mengikut tempoh waranti produk | Traceability dan aduan pelanggan |
| Data pekerja | Semasa tempoh perkhidmatan + 7 tahun | PDPA 2010 dan undang-undang buruh |

## 4. Seni Bina Data Lake untuk Kilang Pintar

### 4.1 Apakah Data Lake?

**Data Lake (Data Lake Kilang / 数据湖)** adalah repositori terpusat yang menyimpan semua data kilang dalam format asalnya (raw) — berstruktur mahupun tidak berstruktur — sehingga ia diperlukan untuk analitik atau AI.

**Perbezaan Data Lake vs. Data Warehouse:**

| Aspek | Data Lake | Data Warehouse |
|---|---|---|
| **Format Data** | Raw, pelbagai format (JSON, CSV, gambar, video) | Berstruktur, skema tetap |
| **Transformasi** | Schema-on-read (diproses semasa dibaca) | Schema-on-write (diproses semasa disimpan) |
| **Pengguna** | Data scientist, AI engineer | Analis perniagaan, pengurus |
| **Kos** | Lebih rendah (storan objek) | Lebih tinggi (pangkalan data berstruktur) |
| **Latency** | Lebih tinggi | Lebih rendah untuk pertanyaan yang ditetapkan |

### 4.2 Tiga Zon Data Lake Kilang

Seni bina data lake kilang pintar menggunakan tiga zon yang berbeza:

```
┌─────────────────────────────────────────────────────────────────┐
│  ZON ANALYTICS (Gold Zone / Analytics Zone)                      │
│  Data bersih, dikira, sedia untuk papan pemuka dan model AI     │
│  Format: Parquet, Delta Lake, aggregated tables                  │
│  Akses: Pengurus, penganalisis perniagaan, model AI             │
├─────────────────────────────────────────────────────────────────┤
│  ZON CURATED (Silver Zone / Curated Zone)                        │
│  Data yang sudah dibersihkan dan diseragamkan                   │
│  • Nilai hilang diisi / dibuang                                 │
│  • Unit diseragamkan (semua suhu dalam °C)                      │
│  • Nama tag diseragamkan mengikut katalog data                  │
│  • Data daripada pelbagai sumber digabungkan                    │
├─────────────────────────────────────────────────────────────────┤
│  ZON RAW (Bronze Zone / Raw Zone)                                │
│  Salinan tepat data sumber — tidak pernah diubah                │
│  • Data sensor (MQTT, OPC-UA)                                   │
│  • Log SCADA                                                     │
│  • Data ERP (pesanan, inventori)                                │
│  • Imej kamera kualiti                                           │
│  • Log sistem IT                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 4.3 Aliran Data dalam Data Lake

**Langkah 1 — Pengingestian (Ingestion):**
Data dari OT layer (melalui edge gateway) dan IT layer (ERP, MES) dimasukkan ke Zon Raw secara automatik. Alat umum: Apache Kafka, Azure Event Hub, AWS Kinesis.

**Langkah 2 — Pemprosesan dan Pembersihan:**
Pipeline pemprosesan data berjalan secara berjadual atau masa nyata untuk memindahkan data dari Zon Raw ke Zon Curated. Alat umum: Apache Spark, Azure Databricks, dbt.

**Langkah 3 — Pengagregatan dan Pengiraan:**
Data curated digabungkan dan dikira untuk menghasilkan metrik dan ciri untuk model AI. Contoh: OEE setiap 15 minit, kadar kecacatan per syif. Ini menghasilkan data di Zon Analytics.

**Langkah 4 — Penggunaan:**
Data dari Zon Analytics digunakan oleh:
- Model AI (baca sebagai input ciri)
- Papan pemuka Power BI / Grafana
- Laporan operasi automatik

### 4.4 Platform Data Lake untuk Konteks Malaysia

| Platform | Persekitaran | Kos (Anggaran) | Sesuai untuk |
|---|---|---|---|
| **Azure Data Lake Storage Gen2** | Microsoft Cloud | RM 0.018 / GB / bulan | Kilang dengan ekosistem Microsoft |
| **AWS S3 + Glue** | Amazon Cloud | RM 0.021 / GB / bulan | Kilang dengan ekosistem AWS |
| **MinIO (On-Premise)** | Pelayan tempatan | Kos perkakasan sahaja | Kilang dengan keperluan data residency |

> **NOTA PDPA 2010:** Data peribadi pekerja (data biometrik, data kehadiran yang boleh mengenal pasti individu) **tidak boleh** dihantar ke platform awan luar negara tanpa persetujuan yang jelas dan pematuhan Seksyen 129 PDPA 2010 tentang pemindahan data peribadi ke luar Malaysia. Anonimkan atau agregat data sebelum penghantaran ke awan.

### 4.5 Metadata Management dalam Data Lake

Tanpa metadata yang baik, data lake menjadi **data swamp (paya data)** — data ada tetapi tiada siapa yang tahu apa yang ada atau cara menggunakannya.

Amalan terbaik:
- Setiap dataset mesti didaftarkan dalam **katalog data** (data catalogue) — boleh menggunakan Apache Atlas, Azure Purview, atau AWS Glue Data Catalog
- Setiap fail data mesti mempunyai metadata standard: sumber, tarikh, format, pemilik, sensitiviti
- Cari mana-mana dataset dalam katalog menggunakan nama mesin, tarikh, atau jenis data

## 5. Integrasi SCADA / HMI dengan Data Lake

### 5.1 Aliran Data dari SCADA ke Data Lake

```
[PLC/Sensor] → [SCADA Historian] → [OPC-UA/MQTT] → [Edge Gateway]
     → [Kafka Topic] → [Data Lake Zon Raw] → [Pipeline Pemprosesan]
     → [Zon Curated] → [Model AI / Dashboard]
```

### 5.2 Kes Penggunaan Kilang E&E di Johor

**Senario Sintetik (digunakan sebagai contoh dalam KK-01):**

Kilang *Maju Electronic Manufacturing (MEM)* di Nusajaya Tech Park mempunyai:
- 50 mesin SMT (Surface Mount Technology)
- 200 sensor (suhu, getanan, arus)
- Sistem SCADA Siemens SIMATIC S7 berusia 8 tahun
- Sistem ERP SAP S/4HANA di awan Azure

MEM ingin membina data lake untuk menggabungkan data OT dan IT bagi membolehkan analitik AI. Mereka menggunakan seni bina:
- **Zon Raw:** Azure Data Lake Storage Gen2 (data sensor MQTT + data ERP SAP)
- **Zon Curated:** Azure Databricks untuk pembersihan dan penyeragaman
- **Zon Analytics:** Power BI + Azure ML untuk papan pemuka OEE dan model ramalan kegagalan
